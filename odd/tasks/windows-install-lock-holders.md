# Windows install: name the process that holds a busy path

Objective: when a Windows install/reconfigure rename or removal stays busy after the bounded retry, the error names the processes holding files under the root.
Branch: `fix/windows-install-lock-holders` (from upstream/main 4716b3cbc). Delivery: ask-on-risk. Runner: `go test ./internal/shellinstaller/...` (Windows).

## Specs

- S1: The installer currently fails with: "Error: rename C:\Users\devel\AppData\Local\gentle-shell\install C:\Users\devel\AppData\Local\gentle-shell\install.replaced-20261123T081053Z: Access is denied.; a file under C:\Users\devel\AppData\Local\gentle-shell\install is still in use by another program (for example an antivirus scan or an open editor or terminal); close it and retry". When the path is still busy after the existing retry in `internal/shellinstaller/user_busy_windows.go` (`userWindowsRetryBusy`), the error must also list the processes (PID and name) that the Windows Restart Manager reports as holding files under the root, so the user knows what to close. In the observed incident this would have named `engram.exe` (holding `install\home\.engram`).
- S2: Identification is diagnostic only: the installer never kills or stops any process. If Restart Manager is unavailable or fails, the existing message is kept unchanged (no new failure mode). The returned error still unwraps to the original Windows error (`errors.Is` keeps working).
- S3: Restart Manager cannot see directory handles held as a process current directory (in the incident: `wsl.exe`/`wslhost.exe` launched with their working directory inside the install tree). Whenever enumeration succeeds (holders found or not), the message must say that a program may also be running with its working directory inside the root (for example a terminal or a WSL session). Assumption: keep the existing message text as a prefix so existing tests and users' searches still match.
- S4: Bounded cost: enumerating files under a large tree (the incident tree had 42,236 files) must stay bounded (cap the number of files registered, and the enumeration runs only on the final failure, never on every retry).
