# Windows private report leaf — fail closed until native proof

## Outcome and authority

Implement the Windows half of approved [issue #4935](https://github.com/Gentleman-Programming/gentle-ai/issues/4935): given a **user-approved absolute destination**, write a new private report of 1–256 KiB only when its path, local filesystem, parent authority, and new leaf protection can be proved. This isolated feature worktree started at PR #4938 head `6d8e572a`; its parser-only local commit is `0e5138b4`, **not** permission to ship a writer. There is currently no Windows report writer: `internal/privatefile/report_unsupported.go` returns `ErrUnsupported` on Windows; `internal/privatefile/windows_parent_windows.go` only walks children relative to a *borrowed trusted root* and does not create a leaf or establish root trust. Preserve unsupported behavior until all three units and the release gate below pass.

> **Blocking design gap:** `WriteNewReport(absoluteDestination string, payload []byte)` accepts only a path and bytes; it has no caller-provided trusted root handle. The existing parent opener cannot manufacture that trust from a path string. Unit 1 must establish a defensible root from the public path without a check-then-open string race, or propose an explicit API/authority change for approval. Do not silently treat `filepath.IsAbs`, `EvalSymlinks`, `Lstat`, a drive-letter prefix, or `os.Open(path)` as a trusted anchor. The Windows filesystem/ACL guarantees needed to claim owner-only containment on an arbitrary user-approved path are **uncertain**, not assumed. If provenance or semantics cannot be proved on the actual filesystem, return `ErrUnsupported` without creating a destination. User approval of a location does not imply safe storage.
