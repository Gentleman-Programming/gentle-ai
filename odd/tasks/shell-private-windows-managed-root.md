# Windows private report: managed LOCAL PRIVATE destination (plan only)

## Decision and boundary

User selected a **managed local private Windows save destination**, not an arbitrary absolute path, UNC share, device path, or remote volume. This plan starts in the dedicated worktree `feat/shell-private-windows-managed-root-03` at exact PR #4950 head `fd74e63b49857b13c29e787994ccbcc74e035c0d`. It supersedes the arbitrary-path *writer goal* in `odd/tasks/shell-private-windows-leaf.md`, not its fail-closed requirements. Existing `windows_root_windows.go` parses strings only; `windows_parent_windows.go` opens children from a **borrowed trusted handle**, closes intermediate handles on return, and provides no owner/ACL proof. `report_unsupported.go` keeps Windows `WriteNewReport` at `ErrUnsupported`. The planning invocation changed only this tracker; this subsequent 1a registration milestone commits only the tracker and CI, without source, tests, writer, save, push, or PR.

The proposed destination is an **existing, application-dedicated private directory beneath the current user's `FOLDERID_LocalAppData`**, with a new exclusive report leaf. Derive its final name from the established report naming contract in unit 3; do not interpret a caller-supplied absolute path as authority or silently fall back to another directory. `KnownFolderPath(FOLDERID_LocalAppData)` supplies a **string, not authority**. The managed directory is not assumed private just because it is under LocalAppData. If it does not exist or any guarantee below is missing, refuse without creating it; provisioning a new managed directory would need its own proved, bounded work unit. Display the resolved intended destination **before** seeking separate post-failure save consent. A failed run's report must not be saved merely because the run is Ready or the user previously chose managed storage; Ready for work/delivery is distinct from permission to save a failure report, and a save failure cannot turn failed work into Ready.

**Security claim limit:** filesystem-reported `nonremote` is NOT proof of a physical medium. Even NTFS, `FILE_PERSISTENT_ACLS`, a disk-type handle and available same-handle locality/virtualization signals are only evidence under an explicitly documented **trusted Windows OS storage stack** assumption; none defeats a malicious kernel, storage driver, or spoofing device. Do not label this a proven physical disk. Unknown/virtual/remote signals or unavailable required checks fail closed. If this narrower contract cannot be established natively, retain `ErrUnsupported` for the writer and ask for a new authority/design decision; do not weaken the gate to ship.

## Key Learnings

- A direct NT mapping and held non-reparse root establish **candidate provenance**, not locality, ACL safety or permission to save; each later proof has its own native RED/GREEN boundary.
- Same-handle evidence depends on a trusted OS storage stack, not provable physical media. Unknown mapping, remote/virtual status, owner or race semantics block the writer.
- An existing managed directory must survive ancestry/DACL and stability checks; absent or unprovable storage blocks save rather than triggering implicit provisioning or falling back to an arbitrary path.
- Consent to save a failed report is distinct from Ready, and native tests must use only disposable fixtures with an outside sentinel.
