## Acceptance rules

These rules govern every verdict below. They are the reviewer's rules, applied literally.

1. **An issue enters the CLOSES list only with evidence.** Evidence is one of: a named test at `719b0f6c` that fails if the fix is reverted; a reproduction verified against a build that contains the fix; or a community confirmation comment posted *after* the fixing commit.
2. **"The code looks related" is not evidence.** Neither is a shared file, a shared package, nor a `Refs #NNNN` trailer. Mechanism identity is required: the commit must address the mechanism the reporter described.
3. **A closure without a pinning test is reported as `fixed, unpinned`,** not hidden. The maintainer decides whether to accept that risk.
4. **File overlap is not supersession evidence** for a pull request. Supersession requires that the PR's invariant is already established by a named commit, or that the code the PR patches no longer exists.
5. **A replacement test counts only if it proves the original invariant and its negative control.** A test that merely exercises the area does not count.
6. **A superseded contract must name its compatibility decision** — breaking, migrated, or silently dropped.
7. **Where supersession cannot be established with evidence, the verdict is `unclear — needs author confirmation`.** Guessing is worse than admitting uncertainty.

## 2.1 Superseded by a different design decision (4)

The issue described a real problem. The release solved a different problem, or solved it a different way, and the issue as written no longer describes the system.

### #1877 — persist and reconcile explicitly unmanaged delivery boundaries

Commit `56370f34` implements the **opposite** of what the issue asks, deliberately. The issue wants a persisted `gentle-ai.rdd-delivery-disposition/v1` record and a `review reconcile-unmanaged-delivery` operation. The maintainer's decision, quoted from the commit:

> The maintainer's answer to what happens to work delivered while reviews were off: it runs the entire review again as if it had never been done. No retroactive reconciliation, no blessing of past unmanaged deliveries. The fresh full review of the current state subsumes the history.

Written into `docs/review-integration.md:172` as the release boundary:

> durable retroactive reconciliation — per-delivery dispositions, retroactive receipts, or any ledger that blesses past unmanaged deliveries — is deliberately not part of this release.

Real fixes did ship alongside it (a zero-byte review can no longer read as `allow`; multiple terminal receipts no longer strand `sdd-status`; archive stops now name the fresh review runnably), pinned by `TestSDDStatusArchiveNeverTreatsAnEmptyCandidateReviewAsCoverage` and `TestSDDStatusReEnableSequenceLandsOnTheFreshFullReview` in `internal/cli/sdd_status_reenable_fresh_review_test.go`. **Recommended action:** close as `wontfix — superseded by design decision`, citing the doc line, rather than leaving it to look neglected.

### #1531 — honouring the 400-line budget via chained PRs is disproportionately expensive

Two decisions supersede it. `cc74e2a4` removes volume as a *tier* input entirely — review tier is now selected by evidence, never size. `55995e8c` retires the Chained delivery-strategy menu option outright ("one delivery-strategy vocabulary, and the Chained option retired"). But `LargeChangeLines = 400` survives at `internal/reviewtransaction/compact_chain.go:228`, now explicitly documented as *a review-composition boundary, not a tier input*. The issue's premise — that the budget drives tier — is gone; its residual cost complaint about composition is not. **Retitle to the composition boundary or close as superseded.**

### #1864 — authorized `review.recover` execute transition omits command

This is a **permanent, test-enforced exception**, not an oversight. `1abfab4c` gave every execute transition a runnable `execute.command` — except `review.recover`, the exact operation this issue reports. `internal/cli/review_transition_command_test.go:150-176` pins the exception with the reasoning: adding `review.recover` to `reviewIntegrationOperationRegistry` would change the published negotiated capabilities array and break five contract tests plus the v1.1–v1.4 fixtures external consumers read. **The maintainer should decide explicitly whether this stays a documented hole.** It is currently invisible to anyone who does not read that test.

### #1865 — benchmark classifies non-executable hints as in-band recovery

Remains true at HEAD, and #1864 keeps it live. `bench/classify.go` `HasEnvelopeContinuation` still accepts `execute.operation` without requiring `execute.command`, and `HasRunnableCommand` still accepts the product name plus one arbitrary token (it gained only `<placeholder>` rejection). **Blocked on #1864's design decision, not on effort.**

## Appendix — how to read a verdict in this document

- A **pinning test** is one that fails if the fix is reverted. Where a fix is docs-only or CI-config-only, no such test exists and the row says so.
- A **stale negative** is a community report of continued failure measured against a build that predates the fix. Two appear in this release (#1881 at `82e1d1f9`, #1872 at `bc4c6b75`). They are not refutations, but they are also not closures — ask for a re-test at `719b0f6c`.
- **`Refs #NNNN` in a commit trailer is not evidence.** Four issues in §2.4 carry one and are not fixed. #1589's fixing commit ships a test asserting the opposite of the closure.
- The prior triage in `docs/audits/data/organic-rdd-recovery/snapshot-ledger.json` classifies all 333 backlog items but records **no evidence** for any of them, and its subsystem contexts (PAD, MMI, EPD) were deleted by `a2f10d8f`. It is a starting hypothesis, not a source of truth.
