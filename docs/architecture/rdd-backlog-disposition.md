## Classification method

The vocabulary is exactly five labels, one per item: `superseded-by-design`, `absorbed-into-wave-N`, `still-valid-fix-now`, `orthogonal`, `unclassified — needs triage`. The baseline is seeded from the closed union of the two source documents (never a live backlog sweep — see `Requirement: Coverage-Map-Bound Baseline Completeness`); one read-only GitHub GraphQL pass enriched title/state for the seeded numbers only.

Classification is mechanical, applied in this precedence order, so it is re-derivable rather than re-argued:

1. **Security-defect override.** An item the audit itself flags with a possible confidentiality/integrity/authorization impact (its own word: "severe") gets `still-valid-fix-now`, citing the freeze policy's security-defect criteria, regardless of any other membership below. Applied once, to `#1379` (cross-lineage receipt contamination — the design's own Amendment E row).
2. **Design coverage row (highest source precedence).** If the item appears in exactly one row of the design's coverage map, its class is derived from that row's control-reduction disposition:
   | Coverage row | Disposition | Class |
   |---|---|---|
   | Shared candidate relation algebra | MERGE | `absorbed-into-wave-1` |
   | Classified authority disposition | KEEP (redesigned) | `absorbed-into-wave-2` |
   | Single transition owner and generic finalization | MERGE | `absorbed-into-wave-3` |
   | Bounded immutable candidate evidence | KEEP (redesigned) | `absorbed-into-wave-3` |
   | Capability before lifecycle mutation | REMOVE (routes) | `absorbed-into-wave-4` |
   | Thin RDD/SDD bridge | MERGE | `absorbed-into-wave-4` |
   | Receipt-only delivery validation | REMOVE (invalidation writes) | `absorbed-into-wave-5` |
   | Retire legacy active paths | REMOVE (whole mechanism) | `superseded-by-design` — the only REMOVE-with-no-replacement row; the reported site is deleted, not fixed by a wave |

   If an item appears in **two** coverage rows with different dispositions (only `#2126`), that is support for two classes — `unclassified — needs triage`, per the design's own fail-closed ambiguity rule.
3. **Audit initiative cluster (for items not in the coverage map).** The audit's own mermaid "Initiative" diagram already groups every open item it names into one cluster. Reused verbatim as the second-precedence source:
   | Audit cluster | Class |
   |---|---|
   | C1 Lineage and corruption | `absorbed-into-wave-2` |
   | C2 Projection and base | `absorbed-into-wave-1` |
   | C3 Result and evidence | `absorbed-into-wave-3` |
   | C4 SDD and budgets | `absorbed-into-wave-4` |
   | C5 Correction and procedural retry | `absorbed-into-wave-3` |
   | C6 Windows and process | `orthogonal` |
   | C7 Diagnostics and UX | `orthogonal` |
   | C8 Deferred features | `unclassified — needs triage` (audit itself defers judgment pending initiatives A–G) |

   An item in **two** clusters is `unclassified — needs triage` (equal support for two classes — e.g. `#1477`/`#1534`, double-counted under both "Result and evidence" and "Windows and process"; `#1529`, double-counted under "Lineage and corruption" and "Deferred features").
4. **Neither source.** An item named in the audit's PR/issue tables but absent from both the coverage map and every initiative cluster gets `unclassified — needs triage`.
5. **PR inheritance.** A PR named only in the audit's `Pull request disposition` table (`#1517`, `#1504`, `#1550`, `#1549`, gentle-pi `#202`) inherits the class of the issue it is explicitly linked to in that table, plus a note that it tracks that issue.
